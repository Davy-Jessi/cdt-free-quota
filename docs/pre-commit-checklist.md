# 发布前检查清单

> **这份清单是给「fork 之后要公开」的人用的。**
>
> 本仓库的文件里遍布 `<YOUR_*>` 占位符，但**占位符只能覆盖那些形状固定的东西**
> —— 凭据、ID、IP。剩下的一大类是「部署环境特有的选择」：你用了哪种网络方案、
> 挑了哪个域名、给哪些服务分了流。它们**没有固定形状**，一行正则抓不到，
> 但它们合起来就是你的一套可识别画像。
>
> 根因：**模式清单只能找到已经想到的类别。** 所以发布前要做两件事，缺一不可：
> 1. 跑 [`../ci/check-disclosure.py`](../ci/check-disclosure.py) —— 管**形状**与**已知值回流**
> 2. **按下面的清单逐条人读** —— 管**语义**

---

## 一、机械检查（先跑）

```bash
python ci/check-disclosure.py .        # 形状 + 哈希黑名单 + 「脱敏标记落进代码」
sh   ci/assert-policies.sh             # 上面这个 + 策略断言 + 凭据形态 + %-格式化
                                       #   + 未定义名 + JS 语义 + 部署事实（共 7 步，
                                       #   步骤号以脚本输出为准）

# ⭐ 可选但推荐：钩子会让「带真实凭据的提交」根本进不来
pip install pre-commit && pre-commit install

# ⭐ 如果你手上还有那份**未脱敏的原件**，务必再跑这个 —— 它防的是
#    「脱敏把代码改坏了」这一类，上面两个都抓不到：
python ci/compare-code.py <本仓库的文件> <你手上的原件>

# ⭐ 如果你**改过线上资源**（触发器 / 函数配置），跑这个回读一遍：
#    它需要 AK/SK/UID（见 .env.example 第三组），所以不在 CI 里跑。
python scripts/verify-deploy.py
#    ⚠️ 上面那条 `sh ci/assert-policies.sh` 里的第 7 步**只**证明
#       「inventory.json ↔ 文档 ↔ 源码」三方自洽，**不证明线上状态**。
#       CI 没有云凭据，读不到线上 —— 这两件事不能混为一谈。
#       把前者说成后者，正是当初「文档写了 3 个触发器、线上只有 2 个」
#       能活下来的原因。**回读必须真的去读。**
```

**它通过 ≠ 可以发布。** 见下一节。

> 🔴 **也别只看 CI 的绿勾 —— 有一层永远不在 CI 里跑。**
> 泄漏闸的第 ② 层（哈希黑名单）依赖 `ci/.denylist`，而那份名单**按设计不进仓库**
> （它存的是已清除值的 SHA256，低熵值可被穷举还原）。
> 所以每次 CI 输出里都会有「第 ② 层未生效」，而**「CI 全绿」因此证明不了
> 「没有已清除的值回流」**。
>
> 这是有真实代价的：本仓库曾把一个已清除的**凭据常量名**重新写进文档 ——
> 本地跑（有名单）当场报 `[denylist]` 命中，而同一次提交在 CI 上**是绿的**。
>
> **公开前的最后一跑必须在本地做**，判据是 `check-disclosure.py` 说出
> **「第 ② 层已生效」**（而不是那句 `OK no shape or denylist hits`）。

> ⚠️ 机械检查的覆盖面本身就是它的结论边界。说「干净」时，
> 必须同时说清**扫了哪些类别** —— 否则「干净」只等于「在我想到的范围内干净」。

## 二、语义清单（必须人读）

对**每一个文件**问一遍下面这些问题。判据是：
**「这句话里的这个值 / 名字 / 选择，是部署环境特有的，还是任何读者都会有的？」**

### 1. 真实凭据（形状检查能抓，但要确认没漏）
- AK/SK、token、SSH 私钥
- **代理协议的 UUID、REALITY 私钥/公钥/`short_id`**
- ⚠️ 最后这一类**容易被当成「配置」而不是「凭据」** —— 它们都是凭据，都能直接连上你的服务。

### 2. 账号标识
- 16 位账号 UID（**桶名、域名里常嵌它**，别只扫裸数字）
- 邮箱、真实姓名、GitHub 用户名
- 提交者身份（`git log --format='%an <%ae>'`）—— 它在历史里，改文件改不掉

### 3. 真实网络地址
- 任何公网 IP / EIP（**包括「只是提一下」的**）
- 内网网段（VPC CIDR、覆盖网络的网段）
- **组织/服务商信息**：机房所在地、云厂商、区域代码 ——
  它们本身不是凭据，但配上 IP 就是「谁的哪台机器」

### 4. 内部机器名与代号
- 机器名、实例名、hostname、SSH 别名、**任何覆盖网络的节点名/网络名**
- ⚠️ **包括「建镜像脚本里写的默认 hostname」** —— 那会造出一台与你同名的机器
- ⚠️ 包括你自己给设备起的任何代号

### 5. 🔴 网络与工具选择（最易漏，因为它不像「凭据」）
- **你用了哪种网络方案**（overlay / VPN / 隧道产品名）
- **你用了哪个代理面板、聚合器、网关**
- **你选了什么出口**（哪家云、哪个机房、哪个地区）
- **你给哪些服务分了流**（规则集清单 = 你的使用习惯画像）
- 判断标准：**这些是「你的选择」，不是「方案的要求」** ——
  方案对代理侧只提了三条**接口约定**，见 [`proxy-interface.md`](proxy-interface.md)：
  出口必须是被计量的那一个、停机后要能自愈、不能绕过内核网络栈。
  **代理软件、协议、组网方案、分流规则全都不在要求里**，用什么都行。

### 6. 个人配置值
- **伪装 / 回落目标域名**（你挑的那个）
- 配置里的 tag、端点名、用户 name（自取的那些名字）
- 除了方案必需的阈值以外，你自己定的参数取值 —— 只为演示的话一律用占位符

### 7. 指向非公开内容的引用
- 引用了**只在你自己机器上**存在的文件名、章节号、备份路径
- 引用了读者没有的私密文档
- ⚠️ 也包括**「某文件是另一个文件的脱敏副本」**这类自述 ——
  它等于告诉读者「有一个含真凭据的版本存在，而且和这份很像」。

### 8. 失真与过时的断言
- 失效的文件指纹（**要么删、要么明确标注「已失效」并说明怎么自行核对**）
- 错误的 API 名 / 参数名 / 错误码拼写
- 过时的计数（「N 条」）
- 声称「未做 X」而实际已完成，或反之 —— **同一事实在两处说法不一致**

### 9. 教程可执行性
- 有没有步骤**只写了目标、没写方法**？
- 有没有步骤**要求读者拥有仓库没提供的东西**？
- 有没有步骤**按字面执行会有不可逆后果或费用，而警告写在后面**？
- 有没有参数**漏了会让整套设计静默失效**（不报错，只是不工作）？

### 10. 🔴 脱敏有没有改坏代码
- 文本替换会**误伤代码**。真实的形态：给日期做脱敏时，正则把云 API 的
  `Version` 参数也吃了 —— `rpc("DescribeInstances", "2014-05-26", ...)`
  变成 `rpc("DescribeInstances", "<日期已隐去>", ...)`。
  **语法没错、`py_compile` 通过、看起来还「像占位符」**，但每一次 API 调用都会失败。
- 判据：**字符串字面量里的占位符只允许一种形态 —— `<YOUR_*>`。**
  其他任何 `<...>` 出现在代码位置都是事故（`ci/check-disclosure.py` 的 ③ 号规则会报）。
- 更强的判据：跑 `ci/compare-code.py` 比对原件与本仓库版本。
- ⚠️ 版本号、地域、端点、限额这类**看着像日期或看着像配置**的参数最容易中招。

### 11. 个人尺度
- **具体到不可能是公开数据的测量值**（带小数的用量、某次采样的耗时、某条日志的原文）
- **带日期的经历叙述**（「某日踩过」「当时决定…」）—— 它们既是时间线，也是「这套环境存在过」的证据
- **第一人称**（我 / 我们 / 本项目组）

## 三、历史与身份

> 📌 **本仓库自己怎么做**：把**开发过程产物**整体排除在跟踪之外，而不是逐条脱敏 ——
> `openspec/`（变更存档）与 `.claude/`（agent 工具文件）都写进了 `.gitignore`。
> 理由：它们记的是「**这次部署是怎么做的**」（线上产物的指纹、私有副本的路径、
> 线上凭据常量的命名），而不是「读者该怎么做」。**逐条脱敏那类文件是长期负担，
> 因为它们每天都在长新内容。** 文件仍留在本地磁盘，不影响自己用。

```bash
# 文件内容 + 提交信息 全历史
git log --format='%s%n%b' | grep -nE '<你的模式>'
git grep -I -E '<你的模式>' $(git rev-list --all) --

# 提交者身份
git log --format='%an <%ae>' | sort -u
```

⚠️ **注意**：改历史要**三样一起改** —— 文件内容、**提交信息**、**提交者身份**。
一个常见的错：修了文件内容，却在**提交信息里把要删的值原样写了一遍**
（说明「删了 X」时把 X 写了出来）。**描述删除动作时不要复述被删的值。**

**若要发布，历史本身也要考虑**：`git log` / `git blame` 会暴露演进过程。
最彻底的做法是**压成单个提交**（`git checkout --orphan` + 重新提交），
并显式指定匿名提交者（`--author`，别依赖 `user.name`）。

> 🔴 **只压本地历史是不够的 —— 远端也留着旧对象。**
> 你本地 `git log` 干净 ≠ 服务器上干净：**每一次 push 过的版本都还在远端的对象库里**，
> 即使它已经不挂在任何分支上，也能通过 `git fetch <sha>` 或 GitHub 的悬空对象被取回。
> 验证方法（换一个空目录，别在本地仓库里做，否则本地对象会满足查询、给你假结论）：
>
> ```bash
> git init /tmp/probe && cd /tmp/probe
> git remote add origin <你的远端>
> git fetch origin <你怀疑残留的那个 sha>   # 能取回 = 服务器上还在
> ```
>
> **真正清掉的唯一可靠做法是「删库重建」**（或用 GitHub 的 support 请求 GC），
> 而不是 force-push —— force-push 只改引用，不改对象。<br>
> 另外**远端 URL 本身也是身份**：`git remote -v` 里的 `github.com/<你的账号>/…`
> 会随 `.git/` 一起被打包分发。要公开分发的目录，先把 `.git/` 换成重建后的仓库。

## 四、几个容易犯的认知陷阱

1. **「我扫描过了，是干净的」** —— 扫描的覆盖面决定了结论的边界。说「干净」时
   必须同时说清**扫了哪些类别**。
2. **「这个讲得通，应该没事」** —— 讲得通不等于不是个人信息。
   一句「看起来合理」的技术说明，照样可以带上一个真实的 hostname。
3. **「我写了意图」=「我做了」** —— 注释里写「只打印键名、不打印值」，
   和那条命令真的只打印键名，是两件事。**检查实际执行的那一行。**
4. **弱手段的结论不可信** —— 超时定得太短、样本太小、范围太窄，
   都会给出「没有问题」的假结论。**先确认手段够得着，再信它的结论。**
5. **改坏了要能回退** —— 改历史前先 `git bundle` + 目录快照。
