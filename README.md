# cdt-free-quota

**把阿里云 CDT 的免费公网流量额度用满，并且用守护机制把超出量限制在可控范围内。**

> ⚠️ 额度是**两个池子**：中国内地 20 GB + 非中国内地 200 GB，合起来 220 GB。
> 它们是**分开**的 —— 单台机器只能吃**它所在地域所属的那个池子**。所以「用满 220 GB」
> 要靠两台机器，本方案部署一台，目标是**用满所属池子的那份**（非内地 200 GB 或内地 20 GB）。

---

> ⚠️ **先读 [`DISCLAIMER.md`](DISCLAIMER.md)。**
> 本仓库的通常用途被阿里云服务条款明文禁止（ECS《使用须知》：禁止流量穿透，
> 违规最高关停并锁定实例并清退）。仓库里其余内容（额度与计费口径、成本护栏）
> 是中性的，可用于任何合规场合。

---

## 这个仓库解决什么问题

阿里云 CDT（云数据传输）每月送 **220 GB 公网流量**（内地 20 + 非内地 200，两个独立的池子），
但有几个坑让它很难真正用满：

| 坑 | 后果 |
|---|---|
| 免费额度**只对「按流量计费」生效** | 选成固定带宽就一分额度都用不上，还照常计费 |
| 共享带宽的 `InternetChargeType` **默认值是错的** | 不显式写 `PayByDominantTraffic` 就拿不到额度 |
| 按带宽计费**不足 1 小时按 1 小时** | 建一个 800 Mbps 的包、23 秒后删掉，仍收满 1 小时（¥14 量级）。**删包不能止损** |
| 函数计算有**每小时最低消费** | 8 分钟一次的巡检 = 每小时都有调用 = ¥7.9/月，与调用量无关 |
| 云监控数据点**滞后 170~300 秒** | 拿它单独当闸门会漏掉最多 22 GB 的盲区 |
| 额度是**账号级**的，会和账号上其他业务抢 | 守护的阈值不能按「这台机器的用量」设 |

**本仓库把这些坑、以及对应的守护实现，都写下来了。**

## 前置条件

> 这些是**硬性**的，不满足会卡住。逐条附出处或实测依据。

| 条件 | 说明 |
|---|---|
| **阿里云中国站**账号 | 国际站账号体系独立、计价不同，本仓库不适用 |
| 完成**实名认证** | 个人认证官方只列两项：支付宝认证 / 扫脸认证（都需身份证） |
| **常驻可用余额 ≥ ¥100** | 「账户余额（现金）和代金券的总值不得小于 100.00 元」。**这是押金不是消费**，且是**持续**门槛——护闸每次拉起实例都要过这一关。⚠️ **这条来自控制台的拦截提示，帮助文档里没有**（官方 ECS 按量付费页只写「可用额度小于待结算账单会进入欠费状态」，那是**欠费**条件不是门槛）。所以本仓库把它标为【控制台提示】，不是【官方】 |
| 一台能跑 loop 设备的 Linux | 若用自建小镜像，构建需要 `dd`/`losetup`/`mkfs`/`chroot`。**Windows/macOS 做不了** |
| 一个推送通道 | 守护的告警链依赖它。**没有它时告警会静默失效**——护闸看起来在跑，实际永不告警。本教程默认用 [PushPlus](http://www.pushplus.plus/)（微信扫码登录 → **必须先实名认证** → 复制 token）；换任何同类网关都行。⚠️ **未实名的 PushPlus 账号发消息会直接返回 905**，见 [`docs/toolchain.md`](docs/toolchain.md) 第二节 |

## 成本

| 项 | 金额 | 说明 |
|---|---|---|
| CDT 公网流量（额度内） | ¥0 | 220 GB/月，中国内地 20 + 非中国内地 200 |
| ECS（抢占式，香港） | 约 ¥0.01/小时 | 停机即不计费 |
| 共享带宽包 | ¥0（额度内） | 按主流量计费 |
| OSS | 约 ¥0 | 状态文件只有几 KB |
| 函数计算 | **¥0.011 × 有调用的小时数** ≈ **¥7.9/月**（本方案的存活巡检是 8 分钟周期，每小时都有调用） | 见 ⚠️ 下条 |
| **常驻押金** | **≥ ¥100** | **这是押金不是消费**，但要一直放账上 |

> ⚠️ **函数计算那条是设计约束不是估算**：按量付费只要某小时内有**一次**调用，
> 该小时就至少收 ¥0.01。所以**每日 1 次 = ¥0.33/月，每 8 分钟 1 次 = ¥7.9/月** ——
> 差 24 倍，而调用量一模一样。设计任何定时器之前先算「**有调用的小时数**」。
>
> 📌 **¥7.9 是按目录价（¥0.011/CU）算的，会随官方折扣变动。**
> 曾经有过一段 ¥0.000088/CU 的折扣（**2024-08-27 ~ 2026-08-27，已到期、未见续期**），
> 那期间 100 CU 低于 ¥0.01 的最低消费线，实收 ¥0.01/小时 ⇒ ¥7.2/月。
> **现在按目录价：¥7.9/月。** 用之前拿当期单价重算一遍，
> 见 [`docs/pitfalls.md`](docs/pitfalls.md) 第 5 条。

## 已知问题

- 🔴 **没在「真实超额」下停过机。** 守护的整条链路（凭据 → 身份自识别 → 混合口径
  → 推送 → 阈值命中 → 打标签 → OSS 写入 → `StopInstance`）在**降阈值的受控演练**里
  跑通过，`--dry-run` 预检也通过（见 [`SKILL.md`](SKILL.md) 第 5 步）；
  但那两次都不是「额度真的用满了」这个场景 —— **真实超额路径没有端到端验证过**。
  ⚠️ 演练压过阈值之后**必须把阈值改回去**再启动实例，否则一开机就会被立刻再次停机。
- ⚠️ **`--dry-run` 只保证「停机锁」不被写**（实例 tag / `halted` 标志 / 停机前那笔 OSS），
  **不保证演练整体无副作用**：本地状态文件与**周期性** OSS 写入照常发生，
  会把演练用的阈值写进共享对象，而 FC 会读它。详见 [`SKILL.md`](SKILL.md) 第 5 步。
- **`docs/pitfalls.md` 里的数字都标了出处等级**：`【官方】` 有文档原文、
  **`【控制台】`** 只在控制台页面上（帮助文档里查不到）、`【实测】` 只对本机成立、
  `【推断】` 未验证。**不要把【实测】当平台规则用。**
- **控制台有两步无法自动化**（升级至 CDT 计费、领取 FC 新客试用），见 `console/`。后者是**一次性资格，不可重试**。
- ⚠️ **FC 兜底（`scripts/fc-keeper/index.js`）是唯一没有自动化语义检查的代码文件** ——
  它 500 多行，只干一件事：判断**要不要把一台已停机的实例拉起来**。
  历史上它在同一个位置上栽过两次，**两次 CI 全是绿的**：
  1. 把「自己再读一次 OSS」改成「复用外层的 `st`」时，那个 `st` 声明在
     `try { const st = ... }` **块内** —— 块外的分支每次都抛 `ReferenceError`，
     被外层 catch 吞掉，**静默退化成一条 error**。`node --check` 查不出（语法合法）。
  2. OSS 对象**读到了但没有可解析的 `ts`** 时，失联时长被算成 0 ⇒
     「护闸疑似失联」永远不触发，而读取本身是成功的 ⇒ 全程静默。
     （这个形状就是文档里那个「诱饵对象」，而文档写明它**在真实环境出现过**。）

  现在补了一道闸：`ci/smoke-fc-keeper.js` —— **桩掉外部 IO、把 13 个决策分支
  真的跑一遍并断言返回的 `action`**（判据是 action，不是「没抛异常」）。
  已接入 `ci/assert-policies.sh` 第 6 步。这道闸做过**反向验证**：
  把上面两个 bug 分别放回去，它都会红。
  ⚠️ **边界**：它验的是**本文件的决策逻辑**，不是「线上能跑」——后者要靠
  `--dry-run` 演练 + 部署后的 `ver` 断言。
- ⚠️ **`guard-liveness-8min` 这个定时器曾经在线上不存在。**
  文档一直把它列为 3 个触发器之一、并称它是「护闸悄悄死掉」时**唯一**的外部观测手段，
  但线上实际只有 2 个触发器 —— 也就是说那层保护**从未生效过**，而且没有任何东西会告诉你。
  **教训**：文档里写「有 A、B、C 三个」时，要有一条**回读**去证明 C 真的在；
  否则「写了」和「有了」是两件事。已按文档补建并**等它自主触发过一次**才确认
  （手工构造事件验证不了真实 payload 形状）。
  排查手法：`aliyun fc ListTriggers --functionName <fn>` 列出来数一遍，
  再对每个名字 `GetTrigger` —— 名字错了会直接报 `TriggerNotFound`，比逐个猜快。

## 发布前的自检

如果你 fork 了这个仓库、把自己的部署参数填进去之后再公开：

```bash
# 0) 可选但推荐：装上提交前钩子，凭据根本不会被 commit 进来
pip install pre-commit && pre-commit install

# 1) 跑那几道闸（每次 push 也会在 CI 跑）
sh ci/assert-policies.sh
```

> ⚠️ **`ci/.denylist` 不在仓库里**（它只存你清除过的值的哈希，且必须放在仓库外）。
> 没有它时输出会**显式告诉你「第 ② 层未生效」** —— 这时那句 `OK` 只代表形状检查通过。
> 详见下面 `check-disclosure.py` 那一段。

- [`ci/check-disclosure.py`](ci/check-disclosure.py) —— **形状检查**（凭据 / 账号 ID /
  资源 ID / 公网 IP / 32 与 64 位 hex）+ **哈希黑名单**（把你自己清除过的值以 SHA256 记住，防回流）。
  ⚠️ 黑名单**只存哈希、不存原文**，而且必须放在仓库外（`ci/.denylist`，已 gitignore）——
  名单本身进了仓库就成了一份敏感值清单。
  ⚠️ **`ci/.denylist` 不存在时第 ② 层是空转的** —— 脚本会显式打印一行提醒，
  不会再静默 `OK`。「这层没在跑」和「这层跑了没问题」必须能区分开。
  ⚠️ **写名单时注意**：名单里的哈希必须是**切分后 token** 的哈希，不是原文的 ——
  含 `=`/空格的值、以 `_` 开头的值，直接对整串做 sha256 是**对不上**的。
  **加完必须做一次正向测试**（把值写进临时文件、跑一遍、确认真的报 `[denylist]` 命中）。
- [`ci/compare-code.py`](ci/compare-code.py) —— **代码结构比对**（`python ci/compare-code.py <本仓库的文件> <你本地那份>`）。
  脱敏是一堆文本替换，而文本替换会**误伤代码** —— 它比对函数集合、API 调用（动作名 + **版本号** + 端点）
  与其余常量，忽略注释和凭据。**只有跑过它，才敢说「脱敏没改坏逻辑」。**
- [`docs/pre-commit-checklist.md`](docs/pre-commit-checklist.md) —— **必须人读的语义清单**。
  机械检查够不着**「这是部署环境特有的选择」**这一类：用了哪种网络方案、哪家云、
  挑了哪个域名、给哪些服务分流。它们没有固定形状，只能靠读懂内容。
- [`ci/check-inventory.py`](ci/check-inventory.py) + [`scripts/verify-deploy.py`](scripts/verify-deploy.py)
  —— **部署事实**这道闸，**分两半，别混为一谈**：
  - `check-inventory.py`（进 CI，**离线**）：`inventory.json` ↔ 文档 ↔ 源码三方自洽。
    CI 里没有云凭据，**它读不到线上** —— 三方都写对而线上依然错，是完全可能的。
  - `verify-deploy.py`（**需要 AK/SK/UID**，部署时自动跑）：真的去线上逐一回读
    触发器名字 / 类型 / cron / **启用状态** / payload、env 键、runtime、`ver`。
  ⚠️ **为什么要有这道闸**：`provision/README.md` §5.3 把 3 个触发器都写对了、
  还专门警告 `guard-liveness-8min`「别漏掉，它是唯一能在护闸悄悄死掉时告警的机制」，
  而**线上只有 2 个** —— 那个触发器从来没被创建过。
  **「写了」和「有了」是两件事**，中间必须有一次回读。
  ⚠️ 顺带：`ci/smoke-verify-deploy.py` 用 13 个反向用例证明上面那个验证器**真的会报警** ——
  一个「不会报警的验证器」和没有验证器是一样的，而且更糟：它让人以为已经有了。

**闸通过 ≠ 可以发布。**
